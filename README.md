# Network-Framework

一个 Linux 下的 C++17 网络服务器框架:**单 Reactor(epoll)+ 线程池 + 业务回调注入**。

回显、聊天室、HTTP……只需要在 main 里换一个回调函数,框架代码一行不改。

## 特性

- **单 Reactor 多线程**:一个主线程用 epoll 管所有连接,重活交给线程池
- **非阻塞 IO**:socket 非阻塞,谁都不卡
- **4 字节长度头协议**:自动解决 TCP 粘包 / 半包
- **业务回调注入**:换一个回调 = 换一个业务
- **心跳检测**:超时没动静的连接自动踢掉
- **优雅关闭**:先排空发送缓冲再断连,消息不丢
- **异步日志**:不阻塞业务,支持 `logger.conf` 配置

## 架构总览

整个框架就两层,记住两个词:**前台 / 后厨**。

- **前台 = 主线程**:一个线程跑 `EpollServer` 主循环,用 epoll 同时盯着所有 socket。
- **后厨 = 线程池**:多个 worker 线程从任务队列抢活,真正处理数据。

```
客户端 ──TCP──▶  ┌──────────────────────────────────────────────┐
客户端 ──TCP──▶  │            主线程 = 前台(EpollServer)          │
客户端 ──TCP──▶  │   epoll_wait 盯着所有 socket                   │
                 │   · 新连接来了   → accept,登记进 epoll         │
                 │   · 数据到了(IN)→ 把任务交给后厨(submit)       │
                 │   · 能发了(OUT)→ 派活:让后厨把缓冲发出去       │
                 │   · 心跳        → 定期扫,踢掉死连接            │
                 └───────┬───────────────────────────────▲───────┘
                         │ 提交任务(submit)               │ 通知前台"这连接
                         ▼                               │ 有数据要发"
                 ┌───────┴───────────────────────────────┴───────┐
                 │             线程池 = 后厨(Worker 线程们)         │
                 │                                              │
                 │   Worker 抢到一个任务:                         │
                 │     recv 收数据 → 拆包 → 业务回调 → 塞发送缓冲   │
                 └──────────────────────────────────────────────┘
```

关键分界:**前台只负责"发现事件、派活"(epoll_wait → accept / submit / 心跳),真正的 `recv`、`send`、拆包、业务回调全部在 worker 线程里执行**。慢活丢给后厨,主线程永远不被卡住。

## 通信协议

```
[4 字节长度(网络序 uint32)] [消息体]
```

TCP 是字节流,本身没有"消息"边界——一次 `recv` 可能只读到半条,也可能一次读到好几条。所以每条消息前面带一个长度头,接收方按长度"知道读到多少算一条完整消息"。拆包在 `Connection::processBufferedData()` 里做。

## 核心模块

| 模块 | 一句话职责 |
|---|---|
| `MessageQueue` | 任务仓库:锁 + 条件变量 + deque。有两种塞法:`push`(满了阻塞等,网络用)、`pushOverrunOldest`(满了丢最旧,日志用) |
| `WorkThread` | 无限循环 "pop 任务 → 执行" 的线程,队列空就睡,任务抛异常也不杀线程 |
| `ThreadPool` | 管一群 worker,对外只暴露 `submit`(返回 `future` 能拿结果);线程数传 0 时自动用 CPU 核数 |
| `Connection` | 每个客户端的档案袋:收/发缓冲 + 状态;负责拆包、塞包、三态发包 |
| `EpollServer` | 前台心脏:主循环 `epoll_wait` → 分发(accept / 交后厨 / 真正 send / 心跳) |
| `Logger` | 异步日志,不阻塞业务;`logger.conf` 可配置级别 / 格式 / 输出目标 |

## 软件设计决策

> 每个"坑"背后都对应一个设计决策,这也是本项目最值得讲的部分。

1. **EPOLLONESHOT(一次性触发)** —— 事件触发一次后自动失效,必须重新 `epoll_ctl MOD` 才能再触发。
   *原因*:一个 fd 同一时刻只会被一个 worker 处理,不会两个线程抢同一个连接。

2. **非阻塞 IO** —— `recv` 没数据会立刻返回 EAGAIN,`send` 缓冲满也立刻返回,而不是卡住线程。
   *原因*:主循环一旦卡在 recv/send 上,其他所有连接的动静都没人管了。

3. **发送缓冲三态**(SentAll / Pending / Error)—— 一次 `send` 只试一把,发不完剩下等 EPOLLOUT 续发。
   *原因*:TCP 发送缓冲可能满,`send` 不该死等,也不能无限循环发,靠 epoll 的可写事件"有空再发"。

4. **业务回调在锁外触发** —— `handleClient` 里拆包拿锁,回调 `handler_` 在锁外调。
   *原因*:回调要调 `server.sendTo`(它要拿 `client_mutex`),`std::mutex` 不可重入,锁内触发就死锁。

5. **广播要主动注册 EPOLLOUT** —— 塞完别人的发送缓冲后,对方并没有新事件,没人会去发它。
   *原因*:主动把对方的监听改成 `EPOLLOUT | EPOLLIN`,epoll 报告可写 → 走已有的 `handleWrite` 发送。

6. **心跳用时间驱动,不用 epoll 超时** —— 主循环每 10 个 tick(约 1 秒)扫一遍所有连接,超时的踢掉。
   *原因*:一个连接空闲时不产生任何事件,只能靠主循环"定时巡检"发现它。

7. **优雅关闭** —— 收到对端 `recv == 0` 时,先把发送缓冲排空再 `close`;`handleWrite` 里发完才 `shutdown(SHUT_WR)`。
   *原因*:对方断开时可能还有没发完的回复,直接 close 会让数据丢失。

8. **日志丢旧保新** —— 日志队列满时丢最旧的,新日志优先。
   *原因*:worker 写日志不能卡(会阻塞业务);时序上新的日志比旧的值钱。

## 编译与运行

Linux 下,在项目根目录执行 `build.sh`(已写好编译命令),产物是 `server.out`:

```bash
./build.sh
./server.out                 # 默认端口 8888
./server.out -p 9090         # 换端口
./server.out -t 4            # 指定线程数(默认 0 = 自动用 CPU 核数)
./server.out -h 30           # 心跳超时(秒,默认 60)
```

> ⚠️ 注意:`-h` 是 **heartbeats(心跳超时)**,不是 help。

## 性能压测

`stress_test.py` 实测(环境:虚拟机 + VS Linux 编译;**回显**业务,payload 64B,每客户端 20 条消息):

| 并发 | 成功请求 | QPS | 平均延迟(ms) | 最大延迟(ms) |
|---|---|---|---|---|
| 100 | 2000 | 19824 | 3.21 | 11 |
| 500 | 10000 | 8604 | 10.00 | 225 |
| 1000 | 20000 | 16329 | 16.77 | 236 |

> ⚠️ **数字只代表当前测试条件**:换成聊天室广播会更慢,消息变大、连接变长都会影响。当前架构是「单 Reactor + 线程池 + 全局锁」,高并发下锁竞争仍带来尾延迟(1000 并发最大延迟 236ms)。
