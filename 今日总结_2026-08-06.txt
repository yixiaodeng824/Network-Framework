一、项目架构确立
------------------------------------------------------------
  生产者(Producer) → MessageQueue → WorkThread × N(由 ThreadPool 管理)
  所有源文件统一放在 src\ 下,VS2022 + C++23(x64 Debug/Release)

二、MessageQueue(消息队列)——已完成
------------------------------------------------------------
  【职责】存储任务 + 线程同步,是整个系统的共享中枢

  头文件:src\MessageQueue.h
  - using Task = std::function<void()>  (任务类型别名,定义在队列里)
  - 公开接口:push(Task) / pop(Task&) / close()
  - 内部成员:
    · std::mutex mtx_              —— 保护 m_tasks 容器
    · std::condition_variable m_cv —— 阻塞/唤醒机制
    · std::deque<Task> m_tasks     —— 任务容器
    · std::atomic<bool> m_closed   —— 关闭标志(原子变量,无锁读写)

  实现文件:src\MessageQueue.cpp
  - push(): 锁内入队 → 锁外 notify_one() 唤醒一个等待的 worker
  - pop(): 加锁 → while(队列空){若已关闭返回false;否则cv.wait睡} → 取出队头 → 返回true
  - close(): m_closed = true(无锁,靠原子变量) → notify_all() 唤醒所有 worker

  【关键设计决策】
  ① 锁只保护 m_tasks 容器,不保护 m_closed(m_closed 用 atomic,更简洁)
  ② 条件变量放在队列里,不放在 worker 里——因为等待方和唤醒方都要碰同一个 cv
  ③ notify 一律在锁外调用,避免不必要的锁竞争
  ④ m_closed 采用 std::atomic<bool>(今日讨论后采纳的方案,替代普通 bool+锁)

三、WorkThread(工作线程)——已完成
------------------------------------------------------------
  【职责】持有线程,循环从队列取任务并执行,不碰锁、不管理队列生死

  头文件:src\work_thread.h
  - 构造:传入 MessageQueue* 指针,构造即启动线程
  - join():等待线程结束
  - 禁拷贝(因为 std::thread 不可拷贝)
  - 无 stop()、无 m_stop——退出靠队列的 close() + pop() 返回 false

  实现文件:src\work_thread.cpp
  - 构造函数:m_thread(&WorkThread::run, this) 启动线程
  - 析构函数:调 join() 等待线程结束
  - run():while(true){pop→若false则break→try{task()}catch打印异常→循环}

  【关键设计决策】
  ① WorkThread 不含任何锁——锁全在 MessageQueue 里
  ② 阻塞靠 pop() 内部的 cv.wait,CPU 不空转
  ③ 每个任务用 try/catch 包住,一个任务崩了不影响线程继续干活
  ④ 退出走队列关闭信号,不再用 m_stop 原子变量
  ⑤ 关闭队列是"管理者"的职责,不是 worker 的职责

四、当前 main 函数(测试用)——已完成骨架
------------------------------------------------------------
  文件:src\ysj.cpp
  流程:创建队列 → 创建 worker → push 任务 → close() → join()

五、今日讨论的重要知识点
------------------------------------------------------------
  1. 锁 vs 原子变量
     - 单值标志(如 m_closed)适合用 std::atomic,简洁且无锁
     - 复合容器(如 m_tasks)必须用 mutex,atomic 保护不了复合操作

  2. 条件变量的归属
     - cv 放在共享对象(队列)里,因为等待方和唤醒方都要访问同一个 cv
     - worker 不需要自己的 cv,它借队列的 cv 睡觉

  3. 退出机制的完整链条
     - 管理者 close() → 队列置标志 + notify_all → worker 的 pop() 返回 false
       → run() 退出循环 → 管理者 join() 等线程结束 → 析构

  4. 职责边界
     - MessageQueue:只管存储和同步,不管谁用、什么时候关
     - WorkThread:只管取任务、干活,不管队列生死
     - 管理者(main/ThreadPool):负责 close + join 的时序,保证不死锁

  5. try/catch 的作用
     - task() 是别人塞的回调,内容不可控,必须包在 try 里
     - 异常逃出线程入口 = 程序直接崩溃,不能恢复
     - cerr 用于输出错误(行业惯例,错误走标准错误流)

  6. VS 项目的文件管理
     - 新建文件时右键 src 文件夹 → 添加 → 新建项,文件才会落在 src\
     - 解决方案资源管理器默认显示虚拟分组(filters),不是磁盘目录结构
     - 切换"文件夹视图"可以看到真实磁盘目录

六、已知问题 / 待改进
------------------------------------------------------------
  1. main 中 push 和 close 存在竞态:worker 线程可能在 push 之前就跑完 pop
     并因队列空+m_closed=false 而睡在 wait 上——目前靠"先 push 再 close"
     的时序勉强保证,多线程下不够健壮(等 ThreadPool 解决)
  2. work_thread.h 同时写了 #include "MessageQueue.h" 和前置声明,冗余,可删前置声明
  3. catch (exception& e) 建议加 const:catch (const std::exception& e)
  4. 文件编码是 GBK,建议改成 UTF-8(不影响编译,但跨平台/工具阅读更友好)
